本次修复不重申旧性能数字。旧报告和可视化所列本轮速度收益均待正确布局下重新测量。

## 本轮保留的修改

- 今日时间线：布局按日期、安排内容与优先安排缓存；滚动位置使用独立观察对象；安排卡片只在内容、选中状态、尺寸、语言或当前分钟等相关条件变化时重新构建。滚动仍按原坐标计算，时间指示线继续更新。
- 周时间线：按日期索引取安排；缓存原始周布局，拖动只重算原位置和目标位置涉及的日期；未变日期的安排卡片保持不变。跨午夜、跨周、隐藏已完成与优先列排布均与原算法对照。
- 拖动预览：使用所属显示器的原生显示回调合并最新输入；松手立即用最终坐标重新计算并提交；退出、取消和销毁时丢弃待处理输入。相同周预览不重复发布。覆盖内部移动、调整时段和外部拖入预览。
- 数据变更：先比较实际结果，再刷新索引、增加内容版本和登记撤销；日期内容与时间安排使用独立版本。项目元数据或单纯安排变化不再使日期快照失效，实际编辑和撤销重做仍刷新。

没有更改数据文件格式、持久化接口、既有拖动吸附参数或轻微回弹风格。

## 未保留的试验

项目子任务改为 `LazyVStack` 后，200 个子任务的初步展开耗时下降，但原生窗口回归发现：反复往返滚动时列表高度从 6098 点变到 6065 点，末尾拖放区域也不能稳定到达。该试验已撤回；新增的滚动往返与末尾目标检查在原布局下通过。不能把试验中的展开收益算入最终结果。后续若继续优化，需要同时解决变高行、折叠测量和拖放目标的可达性。

## 测量口径

`ExperienceWorkloadTests` 使用实际 SwiftUI 页面和原生窗口，Release 构建、1080 × 720 窗口、100 / 1000 条任务与同量安排，单项目 20 / 200 子任务。基线副本位于 `/tmp/dayvdo-experience-20261025-baseline`。前后各五轮串行运行；构建与性能测量分开。原始日志、机器信息、源码校验清单和汇总数据在本地 `Docs/Performance/experience-v081-20261025/`，该目录按现有规则不纳入 Git。

每个样本是操作开始至四次布局/显示等待结束的时间，包含测试等待开销；**不是硬件输入到屏幕发光延迟，不是单帧耗时，也不能据此计算 FPS 或卡顿帧数**。切页使用应用的页面呈现协调器和预加载缓存，但不包含完整侧栏点击链；冷进入指本轮空缓存，不是操作系统冷启动。滚动更新原生滚动容器，缩放及拖动预览更新实际页面状态；排序测量的是保存后的更新，未把它当作真实系统拖放动画测量。

耗时与 CPU 均报告所有样本的中位数及最近秩 p95；单次进入每组仅有 5 个样本，p95 等于最大值。JSON 另保留每轮中位数。CPU 为测试进程用户态加内核态时间，包含后台任务，不等同于主线程阻塞。内存使用 `proc_pid_rusage` 的进程物理占用，另留进程峰值；同进程前轮分配可能保留，不能当作页面独占内存。

### 结果解释

- 密集场景的今日滚动、缩放和周拖动预览改善明显。1000 条数据的五轮周拖动中位数，之前为 274.1–289.5 ms，之后为 64.4–67.2 ms，波动范围分离；今日滚动分别为 51.9–58.2 ms 与 18.4–20.6 ms。
- 100 条数据的今日滚动中位数减少 1.78 ms，p95 基本未变，不承诺日常滚动有明显体感差异。周拖动预览在该合成场景中也减少了更新开销。
- 项目展开、项目滚动、总待办进入，以及大数据的日历进入和筛选未观察到明确、稳定的整体提升；不能因某个统计量略降就归功于本轮修改。200 子任务展开仍约 0.8 秒。
- 压力场景仍有明显瓶颈：周预览更新约 66 ms，周日历进入约 1.3 秒、返回今日约 1.7 秒。数值包含测试协议开销，仍提示需要进一步检查大批视图创建和切页，不能把本轮写成全面流畅。

`dist/DayVDO-InteractionLab.app` 是独立 AppKit 应用。源码与构建方法见 `Tools/InteractionLab/README.md`。可切换原有和候选算法，使用真实鼠标/触控板输入比较吸附、换位、边缘停留、快速反向和 Esc 取消。候选参数：吸附 6/9 点、换位中线缓冲 4 点、36 点边缘内渐进速度上限 240 点/秒、按经过时间追赶缩放目标。

## 验收边界

自动化覆盖布局结果、状态、原生窗口事件、跨日/跨周策略、筛选、撤销重做、排序提交和取消、时间线键盘与编辑器、八语言资源/控制尺寸、深浅色窗口。真实触控板快速反向的每帧体验、完整系统拖动预览动画，以及八语言所有页面的逐屏人工检查没有在此轮冒充为已完成。

能耗代理指标为 CPU、进程中断唤醒、package idle 唤醒和磁盘读写增量。四次测试等待本身会引入唤醒；计数仅覆盖样本区间，延后写入可能落在区间外。测试采用临时数据且正常保存，不以这些计数推导续航百分比。功率、焦耳和电池续航需要独立测量。

## 系统分析结果与缺口

- SwiftUI 模板的一轮诊断运行完整执行并成功保存记录；其内置 Time Profiler 取得 209,996 个采样。主线程采样主要经过 SwiftUI/AttributeGraph 更新和布局路径，原始安排布局函数占比很小。这是带采样开销的单次诊断，不作为前后提升比例，也不是主线程连续阻塞时长。
- 同份记录有 150 条应用卡顿事件，持续时间中位数 16.67 ms、p95 383.34 ms、最大 1783.34 ms；覆盖 100 与 1000 条数据、切页及其他操作。它明确说明压力负载仍有卡顿。没有按操作分配因果，也没有有效的同条件基线，因此不报告“卡顿减少百分比”。记录中的 potential-hangs 表为空；不能把空表解读为没有主线程阻塞。
- SwiftUI 专用更新表没有取得数据，工具明确提示 `Trace file had no SwiftUI data`，因此本轮没有取得视图更新原因图。
- 独立 Animation Hitches 试采成功保存。其后五轮对照试采与上一份记录的后台整理发生重叠，已弃用，不用于比较；后续重试遇到系统采样资源锁 `could not lock kperf`。再次重试时自动审批服务因额度用尽未完成，动作未执行，没有绕过审批。
- Power Profiler 实际报错 `The Power Profiler instrument is not supported on macOS`。功率、焦耳、电池续航均未测量。
- 待完成：有效的前后各五轮系统卡顿次数/持续时间对照、主线程连续阻塞对照；真实输入到屏幕呈现延迟；八语言逐屏人工检查，以及实机减少动态效果和候选手感验收。上述缺口不影响已完成的窗口更新耗时五轮对照，但意味着完整体验验收仍未全部完成。

## 体验检查步骤

1. 在今日时间线选中安排，点击安排外的空白区域，再按 Delete：安排应仍保留。
2. 拖动安排到新时间或相邻日，快速反向后松手：落点应跟随松手位置；Esc 后不得保存预览。
3. 将安排跨午夜调整、跨周移动后撤销/重做：原日与目标日应同时刷新，重叠列位置保持一致。
4. 对总待办筛选后拖动子任务，松手只保存最终顺序；取消恢复，切页返回仍保持已保存顺序。
5. 打开独立手感工具，在同一操作区域切换原有/候选算法，分别比较微调、反向和边缘停留；确认偏好后才将候选纳入正式应用。
